## 1. 为什么这样拆分

PR7 的 `ui/worker.rs` 已经 4700 行，把会话、设置、权限、播报、语音全塞在一起。
PR8 的改动如果继续往里面堆，会变成"旧版巨型主进程的 Rust 复制品"（AGENTS.md 明令禁止）。

因此新增的都是**有单一职责、可独立测试**的模块：

| 模块 | 职责 | 是否依赖 Slint |
|---|---|---|
| `config.rs` | 多提供商、方案、时段、有效窗口、迁移、原子保存 | 否 |
| `clock.rs` | 本地时间（星期/时:分）与可读时间戳 | 否 |
| `model_catalog.rs` | `/models` 解析分类、缓存、连通性测试结果分类 | 否 |
| `session.rs` | 会话文件、索引、原子写、损坏隔离、时间线 | 否 |
| `permissions.rs` | 四档、逐能力覆盖、暂停、限时授权、审计 | 否 |
| `llm.rs` | 协议层；新增 `/models` 原始 JSON 与最小对话探针 | 否 |
| `agent.rs` | 回合循环；事件带回合/步骤/调用实例与真实思考文本 | 否 |

只有 `ui/worker.rs` 依赖 Slint。这样上文全部逻辑都能用 `cargo test` 覆盖，
不需要起窗口。

**替代方案与取舍**：也考虑过把所有状态塞进一个 `AppState` 结构，由 worker 独占。
问题在于：权限判断必须在**工具执行前**读到最新策略，而界面线程要能改暂停/覆盖——
所以权限状态必须是 `Arc<Mutex<PermissionState>>` 共享，不能是 worker 私有的副本。
会话与设置则保持 worker 独占（单一写入者，避免双写冲突）。

## 2. 多提供商配置与迁移

### 结构

`Settings` 在 PR7 的顶层字段（`provider_id` / `base_url` / `model` /
`provider_hint` / `thinking` / `reasoning_effort`）之外新增：

```rust
providers: Vec<ProviderConfig>   // 每家的端点、首选模型、推理档位、已知模型
model_plans: Vec<ModelPlan>      // 命名方案：提供商 + 模型 + 推理档位
model_schedule: ScheduleSettings // 时段规则（默认关闭）
permission_overrides: BTreeMap<String, PermissionOverride>
schema_version: u32              // 升到 2，只用于识别，不做破坏性改写
```

**全部带 `serde(default)`**，所以 PR7 的 `settings.json` 能直接读进来。
读取时若 `providers` 为空，会把顶层字段补成一条条目——**只在内存里补**，
不改写磁盘，也不会碰 Key / 语音 / 播报设置。

Key 仍然走 `secret.rs` 的 DPAPI 按提供商隔离（`secrets/<provider-id>.bin`）。
方案里**不含 Key**：方案只描述"用哪家、哪个模型、哪档推理"，
执行时按方案里的 `provider_id` 去取那一家的 Key。这样切换模型不可能把
MiMo 的 Key 发到 DeepSeek。

### 能力判定顺序（`Settings::profile_of`）

1. 内置提供商若注册表声明了具体协议（MiMo / DeepSeek）→ **以注册表为准**，
   旧配置里残留的 `providerHint` 不得把官方端点带偏；
2. 注册表里的「OpenAI 兼容（自定义）」本身没有协议声明 → 认用户显式填的 hint；
3. 注册表里没有的自定义 id → 同样认 hint；
4. 都没有 → 标准兼容协议（一个专属字段都不发）。

**绝不按模型名猜协议**：`deepseek-flash` 打在自定义端点上仍然是 `Plain`。

### 有效上下文窗口

`context_window_with(configured, trusted_meta)` 只取**更小的那个**：
用户把窗口调到 200K，模型元数据说 131K → 按 131K 算；
元数据比注册表更宽时按注册表。未知端点**不会**被强行改成小窗口——
没有可信元数据就按用户配置走（默认 1M）。

### 会话级选择与时段规则的优先级

```
会话手选  >  时段规则（第一条命中）  >  默认方案  >  全局默认
```

`resolve_selection` 在**发请求前**调用一次并做快照，所以：
- 时段变化不影响已经开始的回合；
- 用户给会话手选模型后，时段规则不再覆盖它。

时段语义与旧版 `schedule.mjs` 一致：`from == to` 全天、`from < to` 左闭右开、
`from > to` 跨午夜、`days` 为空或全 7 天视为每天。

## 3. 模型发现与连通性测试

### 为什么要分成两件事

- **获取模型**：`GET /models` → 解析 → 分类过滤 → 缓存。
- **测试连接**：真的发一次最小对话请求（`max_tokens: 16`，不带工具）。

`/models` 能访问 ≠ 模型能聊天。严格端点会对不存在的模型 404，
所以"测试连接"必须真的打一次 `/chat/completions`。

写进界面的结论刻意分成**可行动**的几类：

| 分类 | 用户该做什么 |
|---|---|
| 认证失败（401/403） | 换 Key |
| 模型不可用（400/404） | 换模型名或检查地址是否带 `/v1` |
| 网络/端点不可达 | 查代理、地址 |
| 其它（429/5xx） | 稍后重试 |

### 分类规则（`classify_model`）

- 有元数据（`type` / `task` / `modalities` / `output_modalities`）→ 按元数据判；
- 没有元数据 → 只剔除**已知非聊天标识**（按整段匹配：`asr` / `tts` / `embedding` …，
  所以 `attest` 不会被 `tts` 误伤）；
- 认不出来的新模型 → **保留**，但标 `ModelSource::Unverified`（界面显示"未验证"）。

这条规则刻意"宁可多留、不可误删"：静态名单永远不是完整目录。

### 缓存

- 内存 + `%APPDATA%\cuava\model-cache.json`；
- TTL 60 秒（切提供商不重复打 API，又不至于看不见上新）；
- 缓存键 `providerId|baseUrl`，并带 Key 的**短指纹**——换账号后不复用旧目录；
- **缓存里绝不存明文 Key**（只有 `长度:散列` 指纹）；
- 请求失败时保留上一次成功的列表（`stale: true`），界面仍能选、模型名照样能手填；
- 缓存读不出来就当空缓存，**不影响设置**。

## 4. 四档权限与逐能力覆盖

### 判定顺序（`PermissionGate::check`）

1. **全局暂停**最高优先 —— 暂停期间任何工具都不执行（含免确认档）；
2. **未知工具**一律拒绝 —— 不因任何档位放行；
3. 档位预设调整**已知能力**的默认级别；
4. **逐能力覆盖**（allow / ask / deny / 跟随档位）压过档位；
5. **限时授权**只把 `ask` 提升为 `allow`，不会解开 `deny` 或未知工具；
6. 风险升级（Win+R、`rm -rf` 之类）在标准档强制 ask，**免确认档不再强制**。

### 免确认的边界（`PermissionMode::PassThrough`）

兑现旧版 `unattended` 语义：

- 已知且可授权的工具**不再询问**（包括默认 deny 的关机/删除类）；
- **未知工具仍拒绝**；
- **全局暂停仍优先**；
- **单项覆盖仍可把它掰回 ask / deny**（留一个刹车）；
- 审计照记，通道标成 `unattended`。

### 解析修复

`PermissionMode::parse` 之前只认 `conservative` / `permissive`，
`"pass-through"` 会被静默解析成 `Standard`——界面显示"免确认"、实际按标准档执行。
现在认 `pass-through` / `passthrough` / `unattended` 三种写法，并有往返测试。

### 临时授权与暂停

- `PermissionState::grant_once(capability, minutes)`：仅本次进程有效，**不落盘**，
  因此不跨会话泄漏、重启即失效；
- `PermissionState::pause(minutes)`：下一个工具判断立刻生效（共享状态）；
- 两者都由界面命令直接改 `Arc<Mutex<PermissionState>>`，不需要重启回合。

### 审计

`AuditLog` 追加写 `%APPDATA%\cuava\audit.jsonl`（JSONL，失败只记 stderr，
不阻断工具执行）。记录字段：时间、工具、能力、级别、决策、通道、脱敏参数、原因、
会话 id、回合 id。

脱敏两层保障（都有测试）：
1. `data:` 开头的 data URL 整段替换成 `[图片数据已省略]`；
2. 任何 ≥ 80 个 base64 字符的连续片段替换成 `[省略]`；
3. 最后整体截断到 120 字。

**这一层是被测试发现后才加的**：原来只按 80 字截断，
一条 `data:image/png;base64,…` 会在截断窗口里留下 20 多字符的 base64。
测试 `audit_records_are_redacted_and_ordered` 直接断言落盘文件里不出现长 base64。

## 5. 会话持久化

### 布局

```
%APPDATA%\cuava\
├── settings.json          全局设置（不含密钥）
├── secrets/<provider>.bin 按提供商的 DPAPI 密文
├── sessions/
│   ├── index.json         列表元数据 + 当前选中项（丢了可重建）
│   ├── <id>.json          每个会话一份
│   └── *.tmp / *.bak      原子写的中转与备份
├── audit.jsonl            权限审计
├── model-cache.json       /models 缓存（不含明文 Key）
└── exports/               审计导出
```

`CUAVA_DATA_DIR` 可覆盖整个根目录（测试用隔离目录）。

### 关键不变量

- **一个会话一份文件**：某个文件坏了只隔离它自己，健康会话照常列出；
  损坏文件**不被覆盖或删除**（用户也许能手工修复），id 出现在 `corrupt` 列表里。
- **索引与内容分开**：索引损坏 → 按会话文件重建（`rebuilt: true`），不丢会话。
- **原子写**：先写 `.tmp`，旧文件降级为 `.bak`，新文件上位成功才删备份，
  失败则还原备份。**绝不先删唯一有效的文件**（PR5 曾因此丢配置）。
- **历史与时间线分开**：
  - `history` 是发给模型的消息（兼容 `ChatMessage`、`context.rs` 压缩、工具配对）；
  - `timeline` 是用户看到的气泡与工具卡片。
  压缩会缩短 `history`，所以时间线**不能**从它推导（有测试直接断言这一点）。
- **附件有界**：保存时 `ChatMessage::for_storage()` 把 `image_url` 段换成
  "（原本附带 N 张截图；恢复时不保留图片）"的说明文字，**结构仍是多段数组**，
  不会被改坏成普通文本。
- **未完成回合**：`TurnStatus` 有 `completed/cancelled/failed/interrupted`；
  恢复时把仍为 `Running` 的工具卡片改成 `Cancelled`（绝不假装成功），
  并把回合标成 `interrupted`，界面据此提示"上一轮没有正常结束"。
  恢复**不会自动重放**任何工具调用。

### 有界性

- 时间线最多 400 条（超出丢最老的）；
- 单条文本最多 4000 字（超出截断并标明原文长度）；
- 每个提供商最多 80 个模型条目。

## 6. 思考内容与工具调用实例

### 事件扩展

```rust
AgentEvent::TextDelta { turn, step, text }
AgentEvent::ReasoningDelta { turn, step, text }   // 流式片段
AgentEvent::ReasoningDone { turn, step, chars, text } // 该步最终文本
AgentEvent::ToolStart { turn, step, call: ToolCallId, name, args_summary }
AgentEvent::ToolEnd   { turn, step, call: ToolCallId, name, status, text, ms }
AgentEvent::ConfirmationRequired(prompt)
AgentEvent::Done(TurnOutcome) / Failed { turn, reason }
```

`ToolCallId` 由"回合 id × 1_000_000 + 回合内递增序号"生成：
**不依赖模型给的 `call.id`**（那可能缺失或被服务端复用），
所以"连续两次 screenshot"一定是两张独立卡片，而不是把最后状态覆盖到同一张。

`ToolStatus` 区分 `Ok / Failed / Denied / Cancelled`——
"被拒绝"与"执行失败"在界面上是两个不同的结论。

### 思考内容

`Agent::run` 之前忽略流式 reasoning 回调，现在：

- `ReasoningDelta` 转发**本次新增**的片段；
- `ReasoningDone` 带该步最终文本，界面用它**替换**流式拼接结果，
  因此同一段 reasoning 不会显示两遍；
- 思考内容只进 `reasoning_chars` 统计与事件，**绝不进 `outcome.text`**——
  所以不可能被 TTS 读到。

模型没返回 `reasoning_content` 时**不会**有任何思考事件：不伪造思考。

### 取消与迟到事件

- 取消时给本批剩余调用补"已取消"终态（状态区分"未执行"与"状态未知"）；
- `dispatched` 集合记录"动作可能已到达桌面"的调用，收尾写"结果未知"，
  不谎称"没执行"（PR5 的 `cancel_truthfulness` 语义保持不变）；
- 事件带 `turn`，界面侧核对归属后才会应用。

### 环境限制（构建路径过长，已实测定位）

本机仓库路径 `D:\Projects\computeruse-voice-assistant\rust`（44 字符）下，
`whisper-rs-sys` 的 CMake 构建目录会展开成

```
rust\target\debug\build\whisper-rs-sys-<hash>\out\build\CMakeFiles\CMakeScratch\TryCompile-<hash>
```

完整路径超过 150 字符后，MSVC 的 `cl.exe` 稳定报
`error D8050 无法执行 c1.dll / 未能将命令行放入调试记录`
（README「构建注意」里记录的正是这个现象）。

**这是一条可绕过的环境限制，不是代码缺陷。** 实测验证：

| 目标目录 | 路径长度 | debug 构建 |
|---|---|---|
| `rust\target` | 约 150+ | 失败（D8050） |
| `D:\wt\t` | 约 110 | **成功**，`whisper.lib` 正常产出 |

所以只要把产物目录放到短路径即可，不必改用 `--release`：

```powershell
$env:CARGO_TARGET_DIR = "D:\wt\t"   # 或任意短路径
cargo build --no-default-features
```

本次 PR8 的验证全部在 `--release` 下完成（当时未定位到原因），
结论本身有效；但构建/测试**也可以用上面的短路径 + debug 完成**。

### 一个必须记住的环境陷阱（已实测确认，不是代码问题）

**现象**：程序能正常启动、能对话，但点「保存」或第一次建会话时报

```
写入配置失败：拒绝访问。(os error 5)
无法创建会话目录（C:\Users\…\AppData\Roaming\cuava\sessions）：拒绝访问。(os error 5)
```

**根因是目录 ACL，不是代码。** `rust\target\release` 目录带有一条可继承规则：

```
icacls rust\target\release
  Everyone:(I)(CI)(DENY)(DC)
  S-1-4-176394349-934181552:(I)(OI)(CI)(W,D,DC)
  ...
```

任何被放进该目录的 exe 都会**继承低完整性标签**：

```
cuava.exe  S-1-4-<沙箱SID>:(I)(W,D,DC)
           Mandatory Label\Low Mandatory Level:(I)(NW)
```

低完整性进程受 Windows 强制完整性控制（MIC）约束，写不了 Medium 完整性的
用户目录 —— 于是 `os error 5`。

**实测对照（决定性证据）**：同一份字节的探测程序，放在不同目录：

| 位置 | 标签 | 写入 `%APPDATA%` |
|---|---|---|
| `D:\cuava-dist\probe_clean.exe` | 无 | `WRITE=OK` / `MKDIR=OK` |
| `rust\target\release\probe_labeled.exe` | Low Mandatory Level | `WRITE=FAIL PermissionDenied (os error 5)` / `MKDIR=FAIL` |

两份文件的 SHA-256 **完全相同**，差别只在标签——所以这不是编译或代码问题，
而是产物所在目录的 ACL 问题。

**解决办法（任选其一，都不需要改代码）**：

1. 把构建产物复制到不在该沙箱目录下的位置再运行（复制到普通目录不会继承标签）：
   ```powershell
   $env:CARGO_TARGET_DIR = "D:\cuava-build"   # 构建到一个正常目录
   cargo build --release --no-default-features
   ```
2. 若已有带标签的 exe，复制一份出来运行即可（`Copy-Item` 出来的文件没有标签）。
3. 以更高权限执行 `icacls cuava.exe /setintegritylevel Medium`（需要管理员）。

**程序侧已做的改进**（代码已改）：保存/建会话失败不再只显示一句
`拒绝访问`，而是给出上面这条可照做的说明；并且**启动时做一次写盘自检**
（写一个临时探测文件再删掉），写不了就立刻在状态栏与设置页提示，
不会等到用户改完一堆设置、点保存时才失败。

## PR8 修复：事件持久化与设置草稿

回合事件通过每回合独立通道返回现有工作线程，由同一 SessionRuntime 更新时间线，回合完成前排空通道。执行中不允许切换会话，因此通道与回合编号共同固定归属，不另建并发会话架构。相比在 Agent 回调中直接改 Slint，这保证重启与实时界面使用同一事实源。

用户提交、工具开始、工具结束及最终思考是落盘检查点；流式正文在内存按相邻回合/步骤合并，不逐 token 同步写盘。写盘发生在后台工作线程，不在音频回调或 Slint 线程。风险是极短的进程崩溃窗口仍可能丢失尚未消费的事件；恢复时执行中的操作统一显示“中断，结果未知”，不声称系统副作用已撤销。

权限设置只编辑 Slint 草稿，保存失败保留草稿且不改运行权限，保存成功才替换档位和覆盖。暂停及限时允许仍即时生效；切换、新建或删除会话清除临时授权但保留全局暂停。模型发现独立任务使用提供商与请求编号回传，避免网络阻塞命令循环；成功目录进入提供商模型列表，失败保留已有模型。

方案编辑复用现有 ModelPlan / ScheduleSettings 与一次保存校验，不另建管理框架。规则表单可编辑开始/结束时间、星期及方案 ID；星期采用 ISO 1–7，留空表示每天。复杂可视化排班不属于本次范围。
