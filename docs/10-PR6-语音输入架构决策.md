# PR6 语音输入架构决策

本文回答三个问题：**为什么这样选**、**有没有别的路**、**风险与扩展点在哪**。
数值都来自本机实测（AMD Ryzen 9 9955HX / RTX 5070 Laptop 8GB / Windows 11），
测法与命令见 [`11-PR6-Whisper对照方法.md`](11-PR6-Whisper对照方法.md)，
脚本见 `tools/bench-whisper.mjs` 与 `rust/examples/whisper_bench.rs`。

PR6 只做「唤醒 → 采集一句话 → 端点 → Whisper 转录 → 交给现有 Agent」，
不做语音合成、语音确认、HUD 与安装器（PR7/PR8）。

---

## 1. 整体链路

```
WASAPI 设备 (cpal)
   └─ 回调：只做 格式转换 + 声道下混
        └─ 有界队列（容量固定，满了计数并丢弃整句）
             └─ 音频线程：
                  ├─ 重采样到 16k 单声道 f32（rubato sinc）
                  ├─ KWS（sherpa-onnx，喂**未增益**的原始 PCM）
                  ├─ VAD（噪声底跟踪 + 迟滞，判断起止）
                  └─ 端点后整句 PCM → ASR 工作线程
                       └─ whisper.cpp（模型常驻，会话间复用）
                            └─ Final 文本 → 现有 UiCommand::Send 语义 → Agent
```

三条硬约束（对应任务书）：

1. 音频回调里**不做推理、不阻塞 I/O、不长时间持锁**；
2. **KWS 用未经过 AGC 的原始 PCM**（旧版实测：AGC 削顶会打乱关键词声学特征）；
3. **Whisper 不在每句话启动一次进程**，模型常驻、跨会话复用。

---

## 2. 采集：为什么是 cpal + 自写前级

**选择**：`cpal 0.18`，Windows 上走 WASAPI 后端。

- 替代方案 A：直接 `windows-rs` 调 WASAPI（IMMDevice / IAudioClient）。
  能省一层依赖并做更细的设备控制（独占模式、事件驱动回调、设备热插拔）。
  代价是要自己处理 COM 生命周期、格式协商、重采样、线程优先级，
  且这些正是最容易写错的部分。PR6 的目标是「可靠地把一句语音变成文本」，
  不是重写一个音频引擎。**当前不选，但保留为后续替换点**——
  采集被隔离在 `voice/capture.rs`，换成 WASAPI 直连不影响上层。
- 替代方案 B：`wasapi` / `cpal` 之外的封装（如 `rodio` 的输入部分）。
  它们不提供输入流的稳定抽象，反而多一层状态。

**前级处理**（`voice/pcm.rs`）：

| 步骤 | 做法 | 为什么不能偷懒 |
|---|---|---|
| 声道下混 | 等权平均 | USB 阵列的有效声道常不在 0；只取第 0 声道近乎静音 |
| 整型归一化 | 按**有效位深**（i16=16、i24=24、i64=64） | CPAL 的 `I24` 用 4 字节存 24 位，按 32 位归一化音量小 256 倍；`I64` 若被当成"不支持的位深"返回 0，会得到整段静音且不报错 |
| 重采样 | rubato `SincFixedIn`，加窗 sinc + 抗混叠低通 | 丢样本会把高频折回可听频段，KWS 漏检、Whisper 错字 |

重采样有回归测试直接卡两件事：44.1k/48k/32k 输入后**能量比接近 1**、
20kHz 输入到 16k 后**残余能量 <5%**（`voice/pcm.rs` 的测试）。

**队列与背压**：回调只做转换后推入固定容量队列（约 4 秒音频）。
满了**不无限堆积**，而是记录溢出计数、丢弃当前这半句并回到监听态。
选「丢整句」而不是「阻塞回调」：阻塞会拖停 WASAPI，整段音频都会失真，
把错的音频送去识别比识别不出来更糟。

## 3. 唤醒词：sherpa-onnx KWS

**选择**：`sherpa-onnx 2.0.1` 的 `KeywordSpotter`，兼容现有 Zipformer 模型与关键词文件。

- 替代方案：自己训一个小 KWS，或直接用 VAD + ASR 做「关键词匹配」。
  后者每句话都要跑一次 ASR，延迟与 CPU 都不可接受；前者属于研究方向，不属本阶段。
- 替代方案：旧版 Node 的 `sherpa-onnx-node`。**明确排除**——PR6 不允许运行期 Node。

**保留的三条旧版实测规则**：

1. KWS 喂**未增益**的原始 PCM（`voice/pipeline.rs` 有注释与测试固定这一行为）；
2. **开口前重置一次 KWS 流**：长时间静音后 sherpa 的关键词流命中率不稳定，
   旧版实测「开麦后第一次唤醒失败」就是这个原因；
3. **每 3 秒静音重置**一次，避免流里堆积几十秒静音。

默认唤醒词沿用「小爱同学」（`x iǎo ài t óng x ué @小爱同学`），
关键词文件按「显式配置 > 数据目录 > 内置默认」的顺序解析，
**不读也不写**旧版 Electron 的目录。

## 4. 端点：为什么自己写 VAD 而不是直接用 Whisper 的 VAD

**选择**：Rust 版噪声底跟踪 + 迟滞状态机（`voice/vad.rs`）。

- 噪声底用最小统计跟踪（向下快、有 -70dB 下限、向上分语音/非语音两档），
  阈值 = 噪声底 + 12dB 起判、+7dB 收尾（迟滞）。
  固定阈值在安静房间会一直误触发、在吵闹环境完全不动——这是旧版踩过的坑。
- 替代方案：Silero VAD（sherpa-onnx 也带）。模型更准，但多一个模型文件、
  多一次推理开销；而这里需要的只是「有没有人在说、什么时候说完」，
  短指令场景下能量+迟滞已经够用。**保留为可选后端**：
  `voice/vad.rs` 的接口只要求「喂块、返回是否语音」，换实现不动上层。

**端点参数**（可在设置里改）：

| 参数 | 默认 | 作用 |
|---|---|---|
| 最短语音 | 250 ms | 短噪声、关门声不触发 |
| 静音收尾 | 700 ms | 说完后多久定稿 |
| 最大语句 | 15 s | 防无限积累，到点强制定稿 |
| 无声超时 | 8 s | 唤醒后一直不说话则回到监听 |

**前文保留**：判定语音起点时，把起点前约 250 ms 的预滚缓冲一起带上，
避免截断首字；端点后再补约 200 ms 尾音，避免吞掉最后一个字。

## 5. ASR：为什么是 whisper.cpp（而不是 sherpa 的流式 ASR）

任务书要求 whisper.cpp，这里记录实测依据与替代方案：

| 方案 | 首字/整句延迟 | 中文短指令 | 备注 |
|---|---|---|---|
| sherpa-onnx 流式 ASR（旧版现用） | 边说边出字，端点即定稿 | 好 | 但 PR6 明确要求 whisper.cpp |
| **whisper.cpp + VAD 端点** | 端点后一次识别 | 好 | 本 PR 的方案 |
| whisper.cpp 直接用自带的 VAD 分段 | 需要额外模型 | 好 | 多一个文件，不在 PR6 基线 |

Whisper 是分段模型，没有真正的流式输出。所以 PR6 **不承诺边说边出字**，
只承诺「VAD 判定说完后给出可靠的 Final」。可选展示 Preview，但 Preview
**绝不进入 Agent、授权或工具链**——这是任务书的硬要求。

### 模型与后端实测（同一段 3.77 秒中文指令）

| 模型 | 后端 | 解码耗时 | RTF | 识别结果 |
|---|---|---|---|---|
| tiny | CPU 16 线程 | 1005 ms | 0.27 | 错字多，不可用 |
| small | CPU 8 线程 | 2335 ms | 0.62 | 正确 |
| small | CPU 16 线程 | 6815 ms | 1.81 | 正确 |
| tiny | **CUDA** | **98 ms** | **0.03** | 错字多，不可用 |
| small | **CUDA** | **205 ms** | **0.05** | 正确 |

（CPU 8 线程那条是本项目 `tests/voice_e2e.rs` 的实测输出；16 线程那条来自
早期独立探针程序。两次数字不同是因为线程数与构建参数不同，不是矛盾。）

结论：**默认推荐 `small` + CUDA**。CPU 基线下 `small` 的 6.8 秒延迟对短指令不可接受；
`tiny` 虽然快但中文准确率明显不足。这不是「为了 GPU 而 GPU」，是实测得出的。

**绑定选择**：`whisper-rs 0.16`（基于 whisper.cpp 1.8.3）。

- 它提供 RAII 的 `WhisperContext` / `WhisperState`，模型可常驻复用；
- `FullParams::set_abort_callback_safe` 让取消能真正打断推理；
- `single_segment`、`no_context`、`set_suppress_blank` 都能配置。
- 替代方案：自己写 `whisper-rs-sys` 级别的 FFI。多出的控制只有
  「自定义 VAD 分段」这类细节，不值得在本阶段维护一套 unsafe 封装。

**CUDA 是默认 feature**：`default = ["cuda"]`，`cargo build --release` 直接得到
CUDA 版本；`cargo build --release --no-default-features` 得到 CPU-only 版本。
两份代码完全相同，只有链接进来的后端不同。

为什么改成默认：CPU 基线下 `small` 单句约 2.3 秒（8 线程），日常短指令已经明显卡顿；
CUDA 是 155~205 ms。把快的那条路做成默认，让不读 README 的人也能得到可用体验。
代价是默认构建需要本机 CUDA Toolkit（`nvcc` + `cudart` + `cublas`）——没有工具链的
开发机/CI 用 `--no-default-features`，这一点写在 README 的构建前置里。

**「请求了 GPU」不等于「GPU 在跑」**：whisper.cpp 的 `whisper_backend_init_gpu`
在找不到设备时返回 `nullptr` 并**静默**退回 CPU，`whisper_init_*` 仍然成功。
所以后端决策与显示都按「实际」来：

| 情况 | 行为 | 界面 |
|---|---|---|
| CPU-only 构建 | 只用 CPU | `Whisper CPU（本构建未启用 CUDA）` |
| CUDA 构建，ggml 看不到 GPU 设备 | **不请求** GPU | `Whisper CPU（没有检测到可用的 CUDA 设备）` |
| CUDA 构建，设备在但初始化失败 | 用同一模型重试 CPU | `Whisper CPU（CUDA：…）` |
| CUDA 构建 + 可用设备 | 用 CUDA | `Whisper CUDA` |
| 模型文件损坏/缺失 | 直接报错，不降级 | `语音不可用：…` |
| CUDA 与 CPU 都失败 | 报错 | `语音不可用：…` |

设备可见性用 ggml 自己的设备枚举（`ggml_backend_dev_count` / `ggml_backend_dev_type`）
确认，不是「用户设置了 use_gpu」。这是项目里**唯一**一处 `unsafe`，理由与风险：

- 必要性：whisper-rs 没有包装设备枚举；它把 raw 绑定放在 `raw-api` 后面，
  而这里只需要三个只读查询函数。
- 替代方案：A) 信任初始化成功 —— 会把 CPU 说成 CUDA；B) 抓 whisper 的日志字符串
  —— 全局日志副作用 + 依赖日志文案，脆弱；C) 起 `nvidia-smi` 子进程 —— 多一个
  外部依赖，而且它看到设备不等于 ggml 能看到可用设备。
- 风险：符号来自 whisper-rs-sys 静态链接的同一份 ggml；上游改名/删除会在**链接期**
  失败（构建错误），不会变成运行期未定义行为。调用只做枚举，不分配、不持有指针。

**应用内回退解决不了什么**：如果 CUDA 运行库 DLL 缺失到进程在 `main()` 之前就
无法启动，任何进程内的 CPU 回退都不会被运行到。本 PR 只保证「进程起来之后」的
行为，并且**不声称**那种环境已验证可回退；统一打包与依赖清单留给 PR8。

## 6. sherpa-onnx 用静态库还是动态库

这是 PR6 里唯一一个真正影响分发形态的选择。

| | 静态（`static`，crate 默认） | 动态（`shared`） |
|---|---|---|
| 随程序分发 | **无需额外文件** | 需要 `sherpa-onnx-c-api.dll`、`onnxruntime.dll` 等约 22 MB |
| 与 whisper.cpp 一致 | 一致（都静态链进 exe） | 不一致：一半静态一半动态 |
| 缺库时表现 | 不会缺 | 启动即「找不到模块」，且要额外维护 DLL 搜索路径 |
| 构建产物大小 | 较大 | 较小 |
| 构建前置 | 需要 `.lib`（官方便携包已含） | 只需 `.dll`/`.lib` |

**选择静态**。理由不是下载速度：官方 `-static-*` 包本来就是为「离线构建/无 DLL 分发」
准备的，而 PR6 没有安装器，越少的外部依赖越好。
代价是 exe 变大，可以接受（whisper 本身就是静态的，总大小以百 MB 计）。

**一个实测踩到的坑，必须写下来**：官方静态包有两个变体——

| 包名 | C 运行时 | 能不能和 Rust/whisper 一起链接 |
|---|---|---|
| `...-static-MT-Release-lib` | 静态 CRT（`/MT`） | **不能**：链接报 `LNK2038 RuntimeLibrary 不匹配（MT vs MD）` |
| `...-static-MD-Release-lib` | 动态 CRT（`/MD`） | 能，Rust MSVC 默认就是 `/MD` |

所以 Cargo 里用默认 feature（static）时，要通过 `SHERPA_ONNX_LIB_DIR` 指向
**`MD`** 那一份已解压的库目录；用 `MT` 版会在链接阶段失败。
`static-MT` 只适合用 `/MT` 编译的纯 C++ 工程。

**当模型文件很大时**，真正影响启动速度的是模型加载而不是链接方式，
所以这两件事不要混为一谈。

## 7. 线程与生命周期

| 线程 | 职责 | 禁止 |
|---|---|---|
| Slint 主线程 | 只画界面 | 任何音频/推理/网络 |
| 采集回调线程（WASAPI 提供） | 格式转换、下混、入队 | 推理、磁盘 I/O、阻塞锁 |
| 音频线程 | 重采样、KWS、VAD、端点 | 模型加载（放到加载线程） |
| ASR 线程 | whisper 推理 | 回调界面（一律走通道） |
| tokio 工作线程 | Agent、CUA、UI 命令 | 不能因为语音卡住 |

**语音的"身份"是 `(instance, session)`**：`instance` 是麦克风实例号（每次「打开麦克风」
+1），`session` 在实例内自增。只用会话号不行——每次启动都从 1 开始，关麦后立刻重开时，
旧实例的 `session = 1` 会冒充新实例的 `session = 1`，把上一句的识别结果送进新一轮。
ASR 返回时按 `(instance, session)` 核对归属：对不上**直接丢弃**，不提交、不播报、不动界面。
清除当前会话也做归属核对（`clear_if_current`），旧回合的迟到完成事件清不掉新回合。

**每个麦克风实例还各自持有自己的活动会话**（`ActiveSession`）。会话号只回答「结果属于哪一句」，
但如果两个时代的实例共享同一份可被**无条件**清空的会话状态，旧线程迟到的 `shutdown()` / `fail()`
仍会把新实例正在识别的那一句抹掉——现象是新实例的 Final 被当成过期丢弃，看起来像
「所有语音都不生效」。所以 `VoiceRoute::open()` 每次换一份新的 `ActiveSession`，
只把当前这份交给 `spawn()`；旧线程继续持有旧的那份，收尾时清不到新实例。
`clear_if_current` 依然保留：它防的是**同一实例内**旧回合的迟到完成。

**状态机不会停在「正在识别」**：有效 Final、空转录、推理错误、太短/无语音、溢出、取消
都会结束会话；识别结束后 ASR 线程回报的是**带身份**的完成事件，音频线程据此回到
`Listening`（而不是靠「活动会话号是否为 0」推断）。

**abort 回调**：现在真的装了（`set_abort_callback_safe`），底层在解码步之间看到取消就
尽快结束。但它只是优化：被取消时仍可能返回半句文本，所以上面的归属核对必须保留。
一个实测踩到的坑：whisper-rs 0.16 的这个接口必须传 `Box<dyn FnMut() -> bool>`；
传裸闭包时它把 `user_data` 还原成错误的类型，回调读到垃圾值，表现为**每次识别**都以
`GenericError(-6)` 失败。这条写在 `voice/asr.rs` 的注释里。

**退出与重开不卡界面**：`Shutdown` 排在正在跑的推理之后，join 有上限
（显式停止 3 s、Drop 300 ms、关麦时对音频线程最多等 700 ms），超时就把线程分离，
由它在推理结束后自己释放模型。Slint 主线程从不等待模型加载或推理。
关麦时那一小段有上限的等待是为了避免旧线程还握着麦克风/GPU 时立刻重开、
出现两个实例同时持有设备。

## 8. 与现有 Agent 的边界

- 语音 Final → 复用 `UiCommand::Send` 语义，走**同一个** Agent 入口；
- Agent 忙、等待点击确认、正在取消时，语音**不启动第二回合**，
  给用户可理解的状态提示，而不是把语音排队延后执行；
- 但设备状态、加载失败、溢出、会话结束这些**合法状态事件照常处理**，
  不会被当成"另一条指令"，也不会因为 Agent 在忙就丢掉；
- 语音文本**不能**充当点击授权的答复。`ask` 权限仍只认点击（PR7 才做语音确认）；
- 唤醒误触发、纯静音、短噪声、空转录、超时、取消的旧会话，一律不触发工具。

**关麦与取消的真实语义**（本 PR 修正）：

- 关麦在**任何**状态（空闲 / Agent 执行中 / 等待点击确认）都真的停止采集，
  让在途识别过期，并进入 `Off`；语音开关偏好的保存失败只影响持久化，不影响关麦。
- 关麦**不是撤销**：已经开始的 Agent 回合继续按 PR5 的取消与权限语义执行，
  不会因为关了麦克风就把已执行/正在执行的操作说成"已撤销"。
- 录制或识别阶段被取消（关麦，或取消当前输入）之后，迟到的识别结果不提交；
  正常有效的结果恰好提交一次（一次性消费，重复事件不会提交第二次）。

## 9. 风险与已知限制

| 风险 | 影响 | 缓解 |
|---|---|---|
| CUDA 版需要驱动 + 运行时 DLL | 分发体积与兼容性 | 默认 CUDA，CPU-only 构建仍可用；README 写明要求；打包留 PR8 |
| CUDA DLL 缺失导致进程起不来 | 无法启动 | 应用内回退无效；文档明确说明，不声称已验证 |
| CPU 版本延迟高（`small` 约 2.3 s/句） | 体验 | 默认构建带 CUDA；UI 如实显示「识别中」 |
| Whisper 中文简体/繁体混出 | 观感 | `language=zh` + 提示词；不做后处理替换以免误改专有名词 |
| 麦克风独占 | 与其它软件冲突 | 共享模式采集，不做独占 |
| 唤醒误触发 | 误提交 | 端点+最短语音+唤醒词三重门槛，且误触发不提交 |
| 频繁关/开麦克风 | 设备与 GPU 被重复占用 | 实例号隔离旧事件；每实例独立活动会话；停止有上限地等待线程收尾；推理接入 abort |
| 关麦时底层推理无法即时中断 | 旧线程仍在算完这一句 | 结果按归属丢弃、不提交；最多等 700 ms 后分离，释放延后但不阻塞界面与新实例 |
