# Computer-Use 语音助手 · 开发方案 v0.1

> 目标：做一个"说一句话，它自己动手操作电脑"的桌面语音助手。
> 复用：DSH NEXT（已装，Electron + Cordis 插件框架，自带 computer-use）作为**执行大脑**；Copilot（已装，闭源）只借鉴**交互形态**，不借鉴代码。

---

## 一、三条结论（先看这里）

1. **不要自己写 computer-use，也不要 fork DSH NEXT。**
   DSH NEXT 2.0.20 里已经带了 `@deepseek-ai/dsh-computer-use` 和 `dsh-experimental-computer-use-cua-driver-native`（截图 + 鼠标键盘 + CUA 驱动），并且跑在 Cordis 插件框架上、自带 HTTP/WS 网关。我们做的是**外挂一层"语音外壳"**，通过会话 API 驱动它。

2. **语音助手 = 一条低延迟流式管道 + 一个常驻悬浮窗，不是一个大模型应用。**
   瓶颈全在链路延迟（VAD 尾点、ASR 出字、TTS 首包），不在模型能力。方案围绕"首字延迟 < 1.2s、可打断"来设计。

3. **架构风险集中在一个点：DSH 的会话 API 是否可外部驱动。**
   本地 61781 端口实测 `/api`、`/health` 均返回 **403**（需要 `~/.dsh` 里的 token）。这是 P0 必须先验证/打通的事，不然后面全盘返工。备选方案已列出（见 §8.1）。

## 三、总体架构

```
  ┌──────────────────────── 语音外壳 Voice Shell (本项目，Electron 44) ───────────────────────┐
  │                                                                                            │
  │  [麦克风] → VAD → 流式ASR ─┐                                        ┌─ 流式TTS → [扬声器]  │
  │                            │                                        │                      │
  │                     对话编排 Orchestrator ─────────────────────────┘                      │
  │                     (状态机/打断/播报策略/确认门)                                          │
  │                            │                                                               │
  │                     DSH Bridge (HTTP+WS, token)                                            │
  │                            │                                                               │
  │  [悬浮HUD] ← 事件流 ←──────┴──── 字幕 / 工具步骤 / 审批卡片                                │
  └────────────────────────────┼───────────────────────────────────────────────────────────────┘
                               │  会话消息 + 工具事件
  ┌────────────────────────────▼──────────────── DSH NEXT（不改源码）─────────────────────────┐
  │  agent-loop → dsh-computer-use（截图/鼠标/键盘/CUA 驱动）+ pwsh/bash + MCP + subagent      │
  │  sandbox-policy / 审批 / 会话持久化                                                        │
  └────────────────────────────────────────────────────────────────────────────────────────────┘
```

**分层理由**：语音链路是高频、低延迟、强实时的；Agent 是低频、长任务、可中断的。两者进程隔离，语音壳崩了不影响 Agent，Agent 卡住也能随时"闭嘴/打断"。

### 为什么是 Electron 而不是 Tauri / PyQt
- 与 DSH NEXT 同版本 Electron（44.7.0），可复用其 preload/窗口/托盘经验，省一周。
- 悬浮窗、透明、置顶、多屏、全局快捷键、音频设备枚举（`navigator.mediaDevices`）都是开箱即用。
- 代价：包体 ~120MB。可接受（本地工具，不分发）。

## 四、技术选型（含为何不选另一个）

| 环节 | 选型 | 备选 & 为什么不选 |
|---|---|---|
| 唤醒/尾点 VAD | **Silero VAD v5（onnxruntime-node）** + 语义尾点（ASR 部分结果静默判定） | webrtcvad 太老、误切多；纯固定静音阈值在嘈杂环境崩 |
| 流式 ASR | **FunASR Paraformer-zh streaming（中文首选，首字 ~200ms）**；英文/多语走 **faster-whisper large-v3-turbo**（GPU, int8_float16） | 只用 whisper：非流式，尾点后才有字，延迟 +600ms；只用云 ASR：要联网+按次计费 |
| 唤醒词 | **openWakeWord**（自定义"嘿，小D"）+ 全局热键按住说话兜底 | Porcupine 要商业授权 |
| 对话大脑 | **DSH agent（DeepSeek 官方模型）**，system prompt 注入"语音模式"约束 | 自己接 LLM 会丢掉 computer-use 工具链，等于重写 DSH |
| 执行 | **DSH 的 dsh-computer-use**（`screenshot` / `click` / `type` / `key` / CUA driver） | 自己写 Windows UIA/pyautogui：跨 App 稳定性差 10 倍 |
| TTS | 主：**edge-tts**（免费、流式、中文自然、首包 ~200ms）；备：**CosyVoice2-0.5B** 本地（可克隆音色，离线） | GPT-SoVITS 音色更好但要训练；Azure 官方 TTS 要 key 要钱 |
| 音频 I/O | Electron 内 `MediaRecorder`/`AudioWorklet` 采集 16k PCM；播放走 Web Audio；VB-Cable 做回灌 | Node 原生 WASAPI 绑定（koffi）只在需要"系统声音旁听"时再上 |
| 通信 | HTTP(REST) 建会话 + WebSocket 收事件流 | 纯轮询：工具步骤是长尾事件流，轮询体验差 |
| 状态管理 | Zustand（渲染层）+ 进程内事件总线 | Redux 过重 |
| 语言/工程 | TypeScript + pnpm workspace + Electron Forge/Vite | — |

## 五、模块设计

### 5.1 目录结构

```
computeruse语音助手开发/
├─ apps/
│  ├─ shell/                 # Electron 主进程 + 悬浮窗渲染层（React）
│  │  ├─ main/               # 窗口/托盘/快捷键/权限
│  │  └─ renderer/           # HUD、字幕、审批卡片、设置
│  └─ voice-core/            # 独立 Node 服务：VAD/ASR/TTS/编排（可脱离 UI 单测）
├─ packages/
│  ├─ dsh-bridge/            # 唯一与 DSH 通信的包（协议适配 + 重连 + token）
│  ├─ protocol/              # 事件与消息的 zod schema（唯一真源）
│  └─ audio-io/              # 采集、重采样、回声消除、VAD 封装
├─ models/                   # 模型权重（gitignore）
├─ docs/                     # 本方案 + ADR + 协议文档
└─ e2e/                      # 播放 wav → 断言最终动作
```

### 5.2 核心状态机（Orchestrator）

```
IDLE ──唤醒/热键──► LISTENING ──VAD尾点──► THINKING ──首token──► SPEAKING
  ▲                    │                      │                    │
  │                 超时/无语音              工具需审批           打断(用户说话)
  └────────────────────┴──────────────────────┴────────────────────┘
                                    PAUSED_FOR_APPROVAL
```
**打断（barge-in）是硬指标**：SPEAKING 期间 VAD 持续监听，检测到人声 → 立刻 `tts.stop()` + 向 DSH 发 `interrupt`，回到 LISTENING。这是 Copilot 语音模式最关键的体感，也是自研最容易漏的。

### 5.3 事件协议（草案，`packages/protocol`）

```ts
type VoiceEvent =
  | { t: "asr.partial"; text: string; ts: number }
  | { t: "asr.final";   text: string; ts: number }
  | { t: "agent.delta";  text: string }                       // 流式 token
  | { t: "tool.start";   name: string; args: unknown; step: number }
  | { t: "tool.end";     name: string; ok: boolean; step: number }
  | { t: "approval.ask"; id: string; action: string; risk: "low"|"high" }
  | { t: "tts.start" | "tts.end"; utteranceId: string }
  | { t: "error";        code: string; message: string };
```

### 5.4 播报策略（决定"像不像人"，不是技术活但最影响体验）

| Agent 阶段 | 播报内容 | 例 |
|---|---|---|
| 收到指令 | 极短确认（<8 字），可配置关闭 | "好，我来" |
| 首个工具调用 | **动作白描**，不说工具名 | "我先打开浏览器" |
| 多步任务 | 每 2–3 步或 >8s 静默才播一次，避免聒噪 | "已经找到那个页面，正在填表" |
| 高风险操作 | **停下来口头确认** + HUD 卡片 | "要删除这 3 个文件，确认吗？" |
| 结束 | 结果 + 一句人话，不复述全过程 | "搞定，文件在桌面了" |

## 六、延迟预算（目标：语音到语音 < 1.2s）

| 环节 | 目标 | 手段 |
|---|---|---|
| VAD 尾点 | 300–500ms | Silero + 语义尾点（看到句子结束符号/标点提前判） |
| ASR 出 final | 150–250ms | Paraformer 流式；partial 已先行，final 只补尾巴 |
| LLM 首 token | 300–600ms | DSH 直连；system prompt 限制"先说话后干活" |
| TTS 首包 | 150–300ms | edge-tts 流式；按句切分，首句 ≤15 字 |
| **合计** | **≈ 0.9–1.6s** | 超过 1.8s 就必须做"预确认语"掩盖 |

> 关键技巧：**不等完整思考再说话**。允许"占位播报"（"嗯…"、"我看一下"）先行，把感知延迟压到 0.5s 内。Copilot 就是这么做的。

## 七、分阶段计划（4 周，每个阶段有可验收产物）

### P0 · 打通桥（2–3 天）｜最高风险，先做
- 装 pnpm、ffmpeg；起 workspace 骨架。
- 摸清 DSH 会话 HTTP/WS 协议：从 61781 的 403 入手，拿 `~/.dsh` token，或读 `dsh-sdk-protocol` 的 schema。
- **验收**：Node 脚本能建会话 → 发一句"打开记事本" → 收到工具事件 → 记事本被打开。

### P1 · 语音闭环（5 天）
- 采集 → VAD → 流式 ASR → 文本上屏（先不接 Agent，回显）。
- edge-tts 流式播报 + 打断。全局热键（按住说话）+ 唤醒词。
- **验收**：说"今天天气怎么样"，1.5s 内听见回复；说话能打断它。

### P2 · 接大脑（4 天）
- dsh-bridge 接会话，token 流式 → 断句 → TTS 队列。
- 工具事件 → 动作白描播报；审批卡片（HUD 上点"允许/拒绝"）。
- **验收**：说"帮我在备忘录里新建一条明天的会议"，全程无键盘。

### P3 · 电脑操作语音化（5 天）
- 高风险动作分级门控（删除/支付/发消息 = 必确认）。
- **指代消解**："点这个"→ 取当前鼠标位置/截图区域，转成坐标给 computer-use。
- 视觉反馈：执行时 HUD 高亮目标区域。
- **验收**：说"把这个弹窗点掉""在右边那个输入框里填我的邮箱"。

### P4 · 打磨与固化（4 天）
- 唤醒词自训、噪声环境调参、断网降级（本地 TTS 兜底）、崩溃自恢复。
- 打包成便携 exe + 开机自启 + 托盘常驻。
- **验收**：录一段 3 分钟无人工干预的完整用例（含打断、确认、失败重试）。

## 八、风险与对策

### 8.1 【高风险】DSH 会话 API 不可外部驱动
现象：61781 直连 `/api` 返回 403，协议未公开文档化。
对策（按优先级）：
1. 用 `~/.dsh` 里的 token 走标准 HTTP 头（最可能只是鉴权）。
2. 走 Electron IPC：以 `dsh-web` 客户端身份注入，或读 `dsh-sdk-protocol` 包里的类型定义反推。
3. 退路：**不做外挂，改成 Cordis 插件**塞进 DSH NEXT（`dsh-experimental-voice-input-bundle` 已经是插件形态，改造成对话式）。代价：耦合、不能独立升级。
4. 最后退路：语音壳只调 `dsh` CLI（`dsh run "..."`）子进程，解析 stdout。能用，但拿不到工具事件流。

> **P0 结束必须给出确定答案**，否则后面三周的形态全变。

### 8.2 computer-use 的可靠性
- 截图-driven 点击在多屏/缩放（本机有 MuMu 虚拟显示器）下坐标易错 → 统一 DPI 感知 + 点击前二次截图校验。
- 对策：所有关键操作"执行后验证"，失败自动重试 1 次并口头报告。

### 8.3 语音误触发 / 隐私
- 唤醒词本地判定，**音频不出本机**；只有识别后的文本上行。
- 麦克风占用冲突（会议中）→ 检测设备占用自动降级为热键模式。

### 8.4 中文 ASR 的专有名词
- 人名/软件名（"飞书" vs "飞输"）→ 注入热词表 + 会话上下文纠错（LLM 一次性改写，成本极低）。
