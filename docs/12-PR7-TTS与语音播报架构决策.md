# PR7 语音合成与播报架构决策

本文回答四个问题：**为什么这样选**、**有没有别的路**、**身份与取消怎么保证**、
**风险与未验证项在哪**。PR6 的语音输入链路见
[`10-PR6-语音输入架构决策.md`](10-PR6-语音输入架构决策.md)。

PR7 的范围是：Agent 的**用户可见回复** → 可选 MiMo-V2.5-TTS 或本地 ONNX TTS →
Rust 原生扬声器播放；支持停止播报、真实语音打断，以及在现有 `ask` 权限流程里
用语音回答「允许 / 拒绝」。**不替换**旧 Electron 发行版，也不是 PR8 的产品化工作。

---

## 1. 整体链路

```
Agent 回合正常完成
   └─ TurnOutcome.text（**只有用户可见正文**）
        └─ 句子切分（顺序、去 Markdown、超长截断并告知）
             └─ 合成后端（二选一）
                  ├─ MiMo-V2.5-TTS：Chat Completions + stream + audio(pcm16)
                  │     └─ choices[].delta.audio.data（Base64，24kHz 单声道 PCM16LE）
                  └─ 本地 ONNX：sherpa-onnx OfflineTts（Kokoro 中英多语言，默认 CUDA、可回退 CPU）
                        └─ 进度回调给出的增量 f32 样本
             └─ 播放层
                  ├─ 生产端：源采样率 → 设备采样率（加窗 sinc 重采样）
                  ├─ 有界缓冲（10 秒，满了生产端等待，回调从不等待）
                  └─ cpal/WASAPI 输出（回调只从内存队列取样本）
```

四条硬约束（对应任务书）：

1. **只播报经过确认的用户可见文本**：`reasoning_content`、工具 JSON、内部提示、
   未完整返回的工具调用都不进入播报路径；
2. **音频回调里不等待**网络、推理或 Slint 线程；缓冲有界，满了让生产端等；
3. **"播完" = 播放缓冲真正排空**，HTTP 结束 ≠ 声音播完；
4. **身份贯穿全链路**：每次播报有 `speech_id`，并绑定发起它的 Agent 回合
   （`turn`）。新播报一开始就换号，旧号迟到的 PCM/网络事件/UI 事件一律丢弃。

---

## 2. 为什么只做两个后端

**选择**：MiMo-V2.5-TTS（标准预置音色）+ 一种本地 ONNX（Kokoro 中英多语言）。

- 替代方案 A：继续用旧版的 GPT-SoVITS。它需要 Python worker、1.5GB 显存、
  6.5 秒模型加载，且音色依赖参考音频。这与"Rust 原生、双击即用"的迁移方向冲突，
  也不是 PR7 的目标。
- 替代方案 B：同时支持多个本地模型族（VITS / Matcha / Kitten / ZipVoice）。
  `sherpa-onnx` 确实都支持，但每个模型族的中文文本前端（词典、tokens、
  espeak 数据）各不相同，同时维护等于把验证成本乘以四倍。PR7 只交付一个
  **通过验收**的模型族；换模型只需要改 `voice/tts/local.rs` 的配置构造。
- 替代方案 C：只用云端。那么断网、无 Key、隐私敏感场景就直接失去语音输出，
  与"本地优先"的产品方向不符。

**不做的事**：音色克隆/设计/训练、插件式 TTS 体系、Python/Node 运行时。

## 3. MiMo-V2.5-TTS：协议与容错

**请求**（`voice/tts/mimo.rs`）：

```json
{
  "model": "mimo-v2.5-tts",
  "messages": [
    {"role": "user", "content": "<可选风格指令>"},
    {"role": "assistant", "content": "<要朗读的正文>"}
  ],
  "stream": true,
  "audio": {"format": "pcm16", "voice": "<可选预置音色>"}
}
```

音频在 `choices[].delta.audio.data`（Base64）里分片到达，官方示例是
**24kHz 单声道 PCM16LE**。非流式形态（`message.audio.data`）也一并识别。

必须扛住的脏数据（都有对应测试）：

| 情况 | 处理 |
|---|---|
| 事件被拆在两个网络块之间 | 按**字节**找 `\n\n` / `\r\n\r\n` / `\n\r\n` 边界，只在拿到完整 UTF-8 后解码 |
| Base64 里切出半个采样（奇数字节） | 残留 1 字节留到下一块再拼；绝不把网络块边界当采样边界 |
| `choices: []`（只带 usage 的收尾块） | 跳过，不是错误 |
| `[DONE]` | 协议结束，不必等连接关闭 |
| `event: error` / 响应体带 `error` | 报失败，附可读原因 |
| 401 / 403 / 429 / 5xx | 翻译成可执行建议（检查 Key / 权限 / 额度 / 稍后重试） |
| 服务端断流 | 报"传输中断"，**不能**当成正常播完 |
| 完全没有音频 | 报"没有返回音频"，不能静默成功 |
| 用户取消 | 立刻结束，不产出任何后续音频 |

**流式播放**：`MimoTts::start` 把请求放进后台任务，`run` 每解出一批 PCM 就
立刻通过通道交给编排层入队播放——**第一批有效 PCM 到达后就能出声**，
不需要等整句（更不需要等整段回复）合成完。

**Key 归属**（安全红线）：TTS **只**从 MiMo 账户（`SecretStore` 的 `mimo` 条目）
读 Key，绝不借用当前对话提供商（DeepSeek / 自定义端点）的 Key；端点固定为
MiMo 官方地址，Key 只出现在 Authorization 头里，不进入错误信息、日志或请求体。
`CUAVA_TTS_BASE_URL` 只用于把请求指向本地 mock / 自建代理（测试与开发），
它不会改变"用哪一把 Key"。

## 4. 本地 ONNX：模型、许可与失败路径

**选择**：`sherpa-onnx` 的 `OfflineTts`（Kokoro 多语言模型），执行提供者默认 **CUDA**
（`localProvider: "cuda"`），运行时拿不到 GPU 就**自动回退 CPU**。

### 4.1 为什么"默认 CUDA"和"单文件分发"在这里冲突

两条事实（已核对 sherpa-onnx v2.0.1 的发布资产与本机实验）：

1. **CPU 版有静态库**：`…-static-MD-Release-lib` 可以把 sherpa + onnxruntime +
   kaldi 全部静态链进一个 `cuava.exe`，**不产生任何需要随包分发的 DLL**——
   这正是桌面单文件分发想要的形态，现在用的就是它。
2. **CUDA 版只有 shared**：v2.0.1 只发布
   `…-cuda-13.x-cudnn-9.x-onnxruntime1.28.2-win-x64-cuda.tar.bz2`（以及 CUDA 12.x 版本），
   里面是 `sherpa-onnx-c-api.dll` + `onnxruntime.dll` +
   `onnxruntime_providers_cuda.dll`（约 268 MB），**没有 CUDA 静态库**。
   原因是 onnxruntime 的 CUDA provider 本身就以独立 DLL 形式存在。

因此 PR7 的取舍是：

- **默认链接静态 CPU 版**，保持单文件；代码里的提供者**默认仍然是 `cuda`**，
  但静态库没有 CUDA provider，创建失败时自动回退 CPU，并把
  `cpu（CUDA 不可用，已回退）` 写进引擎标签与日志——**不假装 CUDA 生效**。
- 想让本地 TTS 真跑 CUDA，需要：改用 shared 链接（crate feature `shared`
  + `SHERPA_ONNX_LIB_DIR` 指向 CUDA 包的 `lib`）、随包带上那 3 个 DLL、
  并安装 cuDNN 9（本机没有，因此**未能实测 CUDA 合成本身**）。
  这条路径会让分发从"单文件"变成"exe + 约 285 MB DLL"，属于 PR8 的安装包议题，
  PR7 不把默认分发形态改掉。
- 需要强制 CPU 的开发/低配机器：`localProvider: "cpu"`。

### 4.2 实测：CUDA 确实更快（RTX 5070 Laptop 8GB / iGPU 空闲 / CUDA 13.0 + cuDNN 9）

同一份文本（中文 + 数字 + 中英混排，约 6.9 秒音频），同一台机器、同一个二进制：

| 指标 | CPU | CUDA | 倍数 |
| --- | --- | --- | --- |
| 预热（模型加载 + 首次推理） | 1 673 ms | 8 517 ms | CUDA 慢 5× |
| **预热后首句** 首音 | 459 ms | **158 ms** | 2.9× |
| **预热后首句** 总耗时 | 1 387 ms | **411 ms** | 3.4× |
| 热路径 RTF（合成 1 秒音频的算力） | 0.201 | **0.062** | 3.2× |

结论：**稳态 CUDA 明确更快**，代价是首次初始化 8.5 秒（cuDNN 句柄 + 显存分配）
和约 1.5 GB 显存。因此运行时做了**后台预热**（`TtsEngine::warm_up`，在
`apply_settings` 之后由独立线程执行）：把 8.5 秒挪到"用户还在配置"的时候，
第一句回复的延迟就是表里的 158 ms，而不是 8.5 秒。

预热是可选的（`fn warm_up(&self) {}` 默认空）：云端后端不会预热，不白花额度。

**怎么开启 CUDA**（默认构建仍是静态单文件 + CPU TTS）：

链接方式现在由 crate feature 决定，**不再需要手改 `Cargo.toml`**
（`sherpa-onnx` 的默认 feature 已关闭，否则 static 与 shared 会同时打开）：

| feature | sherpa-onnx 链接 | 说明 |
| --- | --- | --- |
| （都不开） | 静态库（CPU） | 默认分发形态：单文件、无 DLL |
| `tts-static` | 静态库（CPU） | 显式要求静态链接 |
| `tts-cuda` | shared（GPU 运行时） | 本地 TTS 走 CUDA，需要 `SHERPA_ONNX_LIB_DIR` |

1. `SHERPA_ONNX_LIB_DIR` 指向 GPU 版 sherpa 运行时的 `lib` 目录
   （`sherpa-onnx-v2.0.1-cuda-13.x-cudnn-9.x-onnxruntime1.28.2-win-x64-cuda`）；
2. `cargo build --release --features tts-cuda`；
3. 运行时把 `cublas64_13` / `cublasLt64_13` / `cudart64_13` / `cudnn64_9` 等 DLL
   放进 PATH 或 exe 同目录；
4. 配置里 `localProvider` 默认就是 `"cuda"`，不需要额外设置。

`tts-cuda` 打开时 `build.rs` 会检查 `SHERPA_ONNX_LIB_DIR` 里有没有
`onnxruntime_providers_cuda.dll`（以及 shared 链接需要的 `sherpa-onnx-c-api.lib`），
否则就直接构建失败并给出中文提示——
因为 CPU 版库收到 `provider = "cuda"` 只会打印一句
`Please compile with -DSHERPA_ONNX_ENABLE_GPU=ON ... Fallback to cpu!`
然后**返回成功**，运行期无法可靠区分，界面就可能把 CPU 显示成 CUDA。
`tts-static` 与 `tts-cuda` 互斥，同时开启也会在 `build.rs` 里给出可读报错。

**支持状态的如实表述（重要）**：

- `--features tts-cuda` 现在**可复现地切换链接模式**（不再需要改 `Cargo.toml`），
  这一项是**已实现并验证过构建**的；
- 但 CUDA **合成**本身仍是**实验性**：本仓库的验证环境没有可用的 cuDNN 9，
  因此没有在真实 GPU 上端到端跑通过。构建成功只说明"链接到了 GPU 运行时"，
  **不能**当作"已经在用 GPU"的证据；
- 运行期拿不到 GPU 时 `LocalTts` 会回退 CPU，并把
  `cpu（CUDA 不可用，已回退）` 写进引擎标签——不假装。
  这条回退路径有确定性测试覆盖，与是否真的用过 CUDA 无关。

没有 `tts-cuda` 的构建（默认）里，`localProvider` 即使写 `cuda` 也会直接按 CPU
建引擎，标签显示 `cpu（本构建未启用 CUDA TTS）`——不假装。

- 模型权重**不随源码提交、不自动下载**。目录约定：
  数据目录 `models/kokoro-multi-lang-v1_0/`，或设置里显式指定。
- 需要上游完整资源：`model.onnx`、`voices.bin`、`tokens.txt`，
  以及（有就带上）`lexicon-us-en.txt` / `lexicon-zh.txt` / `espeak-ng-data/`。
  **不自造残缺的中文拼音替代品**——那会得到能跑但读不对的语音。
- 模型**进程内复用**：第一次合成时在独立线程加载，之后所有句子共用；
  退出时随运行时释放。加载与推理都不在 tokio 工作线程或界面线程上。
- 失败路径必须可读：目录不存在、缺哪个文件、音色编号越界、模型与
  `sherpa-onnx` 版本不兼容，都要说清楚；**不能假装合成成功**。
- 许可证：Kokoro 权重由上游发布，分发前需要按其许可核查。PR7 不分发权重，
  安装包如何携带留给 PR8。

与 Whisper 的 CUDA 关系：两者可以同时用 GPU，也可以一边 GPU 一边 CPU
（本地 TTS 回退 CPU 后与 Whisper CUDA 并存，互不影响）。不给本地 TTS
单独加 Vulkan/DirectML 后端：没有实测收益支撑。

## 5. 播放：为什么需要独立的一层

`voice/playback.rs` 不知道"谁在说话"，只做三件事：按格式转换、有界缓冲、
按设备格式输出。

| 决策 | 理由 |
|---|---|
| cpal 原生输出流（进程内） | 不反复启动外部播放器、不每块写临时 WAV；延迟与设备状态都可控 |
| 回调只用 `try_lock` | 拿不到锁就输出静音并计数，**绝不阻塞 WASAPI**；那会让整段音频失真 |
| 缓冲上限 10 秒 | 设备被禁用/占用时，生产端等待比无限堆内存安全；正常播放远低于该值 |
| 低水位 4 秒 | 低于它才继续合成下一句，避免"先攒一整段再开口" |
| 重采样在**生产端** | 回调里不做滤波；24k/22.05k → 48k/44.1k 用同一份加窗 sinc 实现（与采集共用 `pcm.rs`） |
| "播完"以缓冲排空为准 | 只有"没有更多音频 + 队列空 + 设备确实消费过"才算 `finished` |
| 停止 = 清空队列 + 作废当前 `speech_id` | 旧号的后续入队一个样本都不接受；跨回合不会串音 |
| 设备线程独占 `cpal::Stream` | `Stream` 不是 `Send`，必须在创建它的线程里持有；句柄只暴露共享缓冲与停止开关 |

状态机（对用户可观察，状态码稳定）：
`synthesizing → buffering → playing → finished / stopped / failed`。
界面同时显示**实际状态**与一句字幕（当前正在播的那句）。

## 6. 身份规则：三种"停"必须分开

| 操作 | 影响 | 不影响 |
|---|---|---|
| **停止播报** | 清空缓冲、取消未完成的合成请求 | Agent 回合、工具执行、权限请求、麦克风 |
| **取消任务**（现有语义） | 取消 Agent 回合 **并且** 停掉本回合的播报 | — |
| **权限拒绝** | 只结算当前 `ask` 请求（工具不执行） | 播报、其它回合 |

回合失败或中断时**不播报**（把"已中断"读出来只会更困惑）。
新回合一开始先停掉上一轮的声音，绝不接在旧音频后面。
`speech_id` / `turn` 的核对发生在三处：合成任务入队、监控任务上报状态、
工作线程处理界面事件。

## 7. 语音打断：为什么不用能量，也不用 KWS

旧实现的两条实测结论（`packages/voice/bargein.mjs`）：

1. **只用电平阈值不成立**：宿舍里咳嗽一声、室友笑一下都能让助手闭嘴；
2. **PR6 的 Zipformer KWS 对"等一下"这类短词无效**：8 种音素写法 × 12 组阈值
   全部 0 命中，而同一个 Whisper 对同一段音频一字不差。

所以 PR7 的做法是：**播报期间打开"直通聆听"**（不要求唤醒词），
用 VAD 的有声判断决定"有人说话"，用 ASR 的 Final 文本决定"是不是打断词"：

```
VAD 说话起点 → 直通捕获（无唤醒词）→ 端点 → Whisper → Final
   └─ 文本命中打断词（等一下 / 停一下 / 别说了 …）
        └─ 且不是我们自己的回声 → 停止播报
```

**回声防护**（必须）：助手朗读「如果说等一下，我就会停下来」时，麦克风会把
「等一下」原样收回来。判据是保守的：识别结果被正在/刚播过的某一句包含
（或反过来包含），就认定为本机回声，不打断。代价是"用户恰好重复了播报内容"
可能被漏判——比"朗读时自我打断"安全得多。

**明确不做**：不承诺任意音响设备上的完美全双工 AEC，不为这件事重写音频引擎。
外放时本机语音仍可能被识别成**别的**词，PR7 只保证"不因为自己朗读的打断词而打断"。
耳机与低音量外放的实测范围见 `rust/README.md` 的验证章节。

打断词不会被当成新指令送进 Agent：它只用于停止播报，用户需要再说一次指令。

## 8. 语音确认：否定优先 + 请求绑定

`ask` 权限请求现在有两条通道，**竞争结算同一个 pending 请求**：

```
UiConfirmer.pending(request_id)
   ├─ 点击「允许 / 拒绝」 ──┐
   └─ 语音 Final（绑定 request_id）─┴─ 一次性 oneshot 结算（第二次必然失败）
```

判定顺序（`voice/confirm.rs`，纯函数、可确定性测试）：

1. **否定优先**：`不可以`、`不要`、`不同意`、`别执行`、`不行`、`拒绝` …
   只要出现就拒绝。中文里「不可以」包含子串「可以」，先判否定才不会被读成同意；
2. **疑问/条件不算同意**：`可以吗`、`能不能`、含问号 → 不明确；
3. **必须出现明确的肯定词**，且去掉肯定词与语气词后没有实义残留 → 允许；
4. 其余（含糊、混合、过长、称呼开头）→ **不明确**，保持等待（还能点击或重说）。

绑定规则（防止一条迟到的识别结果批准别的请求）：

- 进入语音确认模式时把 `request_id` 写进聆听模式，**开始录这一句时快照**；
- 结算前核对：`bound == 0`（不是确认答复）、没有挂起请求（重复/超时/已点按钮）、
  `bound != pending`（属于已结束的请求）——全部忽略，不结算；
- 关闭麦克风、取消回合、退出都会让在途的这一句过期（PR6 的实例/会话归属核对）；
- **TTS 提示音不能被识别成同意**：确认流程本身不播报提示语，
  且只有 `Final`（完整识别结果）参与判定，不用 partial。

权限语义不变：`allow / ask / deny` 三档、未知工具拒绝、取消是终态
（取消后迟到的"允许"不生效）——这些都在 `permissions.rs` 里已有测试，
PR7 只新增了 `channel = "voice"` 这一条通道。

## 9. 配置与兼容

`settings.json` 新增 `tts` 节，**全部字段带 `#[serde(default)]`**：

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | `false` | 总开关；新安装**不会**把回复文本发到云端 |
| `backend` | `off` | `off` / `mimo` / `local` |
| `speakVoiceTurns` / `speakTextTurns` | `true` | 语音提问、手动输入是否自动播报 |
| `outputDevice` | `""` | 空 = 系统默认输出设备 |
| `mimoModel` / `mimoVoice` / `mimoStyle` | `mimo-v2.5-tts` / 空 / 空 | 音色为空 = 不发送 `audio.voice`，用服务端默认 |
| `localModelDir` / `localSid` / `localSpeed` | 空 / 0 / 1.0 | 本地模型目录、音色编号、语速 |
| `timeoutMs` | 30000 | 单句合成超时 |

- 播报设置与模型端点设置**互不覆盖**（保存端点不会改动 TTS，反之亦然）；
- 保存顺序仍是"先落盘配置、再生效"；引擎建立失败**不回滚用户的选择**，
  只把播报标记为不可用并说明原因；
- 退出时释放 HTTP 流、输出设备与本地模型，不在后台继续联网或推理。

## 10. 未覆盖与风险

| 项 | 状态 |
|---|---|
| 全平台 AEC / 全双工 | 不做。只保证"不因自己朗读的打断词而打断" |
| 任意短词打断 | 只有词表内的短语；不在词表里的话不会打断（会提示"没有打断词"） |
| 云端文本隐私 | 云端模式会把**回复正文**发给 MiMo，界面已明确说明；本地模式不联网 |
| 本地模型分发与许可 | 不分发权重；安装包如何携带留给 PR8 |
| 多句预取 | 首版按整句顺序合成播放，不做预测式预取 |
| 长回复 | 超过 400 字只播前 400 字，并明确提示未播字数 |
| 设备热插拔 | 设备消失时播报失败、文本仍可读；不会自动切到另一个设备 |
| 音色质量 | 不做"高质量"承诺：只有实际试听过的样本才写进验收记录 |
