## 一、R1 · 内置本地备用轻量模型（可手动切换）

### 1.1 定位：不是主力，是"断网/降级"的保险

云端模型仍是主力——computer-use 是长链多步推理，本地小模型在**工具选择准确率**上差距明显。本地模型的职责是：
- 断网 / API 故障时仍能执行**简单指令**（打开应用、截图、点击、输入）
- 隐私敏感场景手动切换（"不要联网"）

### 1.2 硬约束：必须支持 tool calling

computer-use 全靠 function calling。**不支持就只剩聊天，等于没有备用手**。
降级矩阵（切换 UI 必须明示）：

| 本地模型能力 | 可用功能 |
|---|---|
| 支持 tool calling | 全部 computer-use 工具 |
| 仅支持 JSON 输出、不支持 tool calling | 单步操作（自己拼 tool call），无多步规划 |
| 纯文本 | **只能对话，不能操作电脑**（UI 上必须灰掉操作开关） |

### 1.3 选型（候选，均需 P0 实测确认）

| 候选 | 量级 | 为什么考虑 | 待验证 |
|---|---|---|---|
| Qwen3-4B 系（含 tool-call 微调版） | Q4 约 2–3 GB | 中文强、社区有 function-calling 微调与 GGUF 产物 | 工具选择准确率、幻觉率 [未验证] |
| Qwen3-8B 系 | Q4 约 5 GB | 8GB VRAM 可跑，准确率更高 | 显存是否够 + 上下文长度 [未验证] |
| 更小的 1.5B–2B | 1–1.5 GB | 纯 CPU 也能跑 | 基本不可能可靠调用 12 个工具 [未验证] |

**运行时：llama.cpp（内置 `llama-server.exe`）**
理由：单 exe 无运行时依赖、支持 OpenAI 兼容 `/v1/chat/completions`（**我们的 agent loop 不用为本地模型写第二套代码**）、支持 `--jinja` + tool-call parser 解析模型输出为结构化 tool_calls。

> 选 llama.cpp 而非 ONNX/自研推理：省掉一个推理引擎的维护成本，且天然多后端（CUDA/CPU）。

### 1.4 打包与分发

- 二进制（`llama-server.exe` + 依赖 dll）打进安装包，约 30–60 MB 量级。
- **模型权重不内置**，首次运行时从"模型管理"页下载（可离线导入 `.gguf` 文件）。
  理由：内置 3GB 权重会让安装包膨胀到不可接受，且用户可能想换模型。
  → 若要"开箱即用"，可提供一个"精简模式"：内置 1.5B 级模型（~1GB）只保证能开关应用，完整模型按需下载。
- 模型目录 `models/`，文件校验（sha256）+ 断点续传。

### 1.5 切换与降级逻辑

```
设置页：模型来源 [云端 DeepSeek ▾ | 本地 ▾]
                    ↓ 选择本地时
        本地模型 [qwen3-4b-q4.km.gguf ▾]  状态: ●已加载 / ○未加载 / ⚠能力不足
        自动降级 [ ] 云端连续失败 2 次时切本地（默认关闭，避免静默降智）

运行中切换 = 立即生效（新会话），当前会话不打断
```
**关键原则：降级必须"可见"**——HUD 上常驻一个来源徽标（☁ / 💻），切换后语音播报一句"已切到本地模型，复杂任务可能做不了"。静默降级是体验事故。

### 1.6 实测计划（P0 必做）

用 20 条真实语音指令跑两个模型，比对：工具选择正确率 / 参数正确率 / 多步任务完成率 / 首 token 延迟。**在拿到数据前不承诺任何性能数字。**

## 二、R2 · 高风险动作语音确认（重新设计）

### 2.1 先说结论

按你的决定，高风险动作**改为语音确认**。风险分级不变，只改"确认通道"。
但我把「必须点鼠标」换成「语音确认」时，加了 5 道闸门 —— 因为最大的威胁不是 ASR 听错，而是**我们自己的声音触发自己**。

### 2.2 核心威胁：自触发（self-trigger）

```
助手 TTS："要删除这 3 个文件，请说确认删除"
     ↓ 扬声器
   麦克风（同一台机器，无隔离）
     ↓
ASR 识别到"确认删除" → 误判为用户同意 → 文件被删
```
这不是理论问题：本机麦克风阵列与扬声器在同一台设备上，桌面场景回声是常态。

### 2.3 五道闸门

| # | 机制 | 说明 |
|---|---|---|
| G1 | **半双工门（Half-duplex gate）** | TTS 播放期间 + 播放结束后 300ms 内，确认类识别**直接丢弃**。成本近零，挡掉绝大多数自触发 |
| G2 | **回声消除 / 物理隔离** | 优先做 AEC（WebRTC AEC3）；本机已装 **VB-Audio Virtual Cable**，可把 TTS 输出路由到 CABLE Input 再回环，物理上不与麦克风混路 —— 这条最彻底 |
| G3 | **完整短语匹配** | 只接受"**确认删除这三个文件**"级别的完整短语（动作+对象+数量），**拒绝"确认/好/可以/嗯"单字**。且必须与提问时的对象词做**语义匹配**，不匹配则重问 |
| G4 | **时间窗 + fail-closed** | 提问后 8 秒内有效，超时/静音/任何歧义 → 一律视为拒绝 |
| G5 | **声纹校验（可选）** | `sherpa-onnx` 说话人嵌入，注册一次本人声纹；非本人声音 → 拒绝并要求点鼠标。默认关闭，可开 |

### 2.4 分级与确认方式

| 级别 | 典型动作 | 确认方式 |
|---|---|---|
| 低 | 打开应用、滚动、截图、读剪贴板 | 不确认，直接做 + 白描 |
| 中 | 输入文本、点提交类按钮 | 不确认，5 秒内"撤销"可用 |
| 高 | 删除文件、发送消息、改系统设置 | **语音完整短语确认**（G1–G4 全开） |
| 极高 | 支付/转账、密码输入、格式化磁盘 | **建议仍保留物理确认**（理由见 2.5），可配置为语音 |

### 2.5 我保留意见的地方（供你复核）

「极高」这一档我仍建议物理确认，原因：语音信道无法区分"用户在说话"和"用户在放一段录音"。G1–G5 能挡住误触发，但挡不住**主动播放的录音**（除非声纹 + 活体检测，成本远超收益）。
如果你的场景里不存在"被人拿录音指使助手"的风险（单人居所、无访客），那这一档放开语音确认也合理 —— **这是个场景决策，不是技术决策，你来定**。

### 2.6 仍然必需的"急停"

任何语音确认都不能替代急停：**Esc 长按 2 秒 = 立即断开 computer-use 控制**（kill 桥进程），优先级最高，不应答任何确认。

## 三、R3 · 声库 TTS 能否降低延迟？—— 实测结论

### 3.1 直接回答：**看你怎么用，默认不会，但有一种用法会，而且快得多**

| 用法 | 首包延迟 | 判断 |
|---|---|---|
| UTAU 传统整句渲染（每音符起一个 resampler 进程） | 40 音符 × 24.6ms 进程启动 ≈ **1s 起步** + 渲染时间 | ❌ 比 edge-tts 慢 3 倍以上 |
| 预渲染音节库 + 运行时拼接 | DSP 全程 **39ms / 14 秒音频**（实时因子 0.003） | ✅ **可做到 <100ms 首包**，比 edge-tts 的 340ms 快 3–4 倍，且离线 |
| 声库只用于预渲染固定短语 | **0 ms**（本地文件直读） | ✅ 最快 |

**关键结论：声库慢不在拼接，在两处**
1. **每个音符一个 resampler 子进程**（24.6ms/次 × 音符数）—— OpenUtau 内置 resampler 已能消除；
2. **F0 / 时长的预测**——这是"唱"与"说"的本质差别，声库本身只提供音色，不提供韵律。

所以：**声库不是一种"低延迟 TTS 技术"，它是一个音色方案。** 拿它换延迟，方向是错的；拿它换**助手的固定人格声音**，方向是对的。

### 3.2 我建议的三层 TTS（把声库放在它真正擅长的位置）

| 层 | 方案 | 首包 | 覆盖 |
|---|---|---|---|
| **L0 预渲染短语音库** | 高频话术（"好的""正在打开""已完成""需要你确认"）**离线预渲染成音频文件**，播放时直读 | **~0 ms** | 60–70% 的播报量 |
| **L1 在线流式** | edge-tts | 340 ms（实测） | 任意文本 |
| **L2 离线兜底** | sherpa-onnx 本地 VITS/kokoro | [未验证] | 断网 |

**声库在这个结构里的正确用法**：拿术力口声库**预渲染 L0 那批固定短语**——一次性离线渲染，永久复用，既拿到独特音色，又拿到 0ms 延迟。这正好把声库的优势（音色）和劣势（不能实时）都放对了地方。

### 3.3 不建议的做法
- 为实时合成自研 F0/时长模型：工作量远超整个语音助手，收益不明确。
- 混用声库与 edge-tts 音色（一句话里两种音色）：听觉上非常怪。
