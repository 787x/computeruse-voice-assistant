# PR13 第二轮：目录、缓存与清除凭据的一致性

## 实际修改

`ProviderConfig.models` 是已配置模型目录的权威持久数据。`restore_model_catalogs()` 不再删除全部非手动模型：同一地址的完整目录原样保留，不因无缓存、缓存缺 Key 或 Key 清除而消失，也不由旧缓存复活用户已删除的候选。

旧配置（未显式保存启用集合）、空目录和地址变化可从匹配的缓存补充缺失候选，现有 ID 的显示名、元数据和手动修改不被覆盖。旧 URL 的服务端能力继续调用既有失效逻辑，模型及手动条目不删除。旧全局保存入口的 URL 变化也采用此规则，移除了另一个清空目录的历史分支。

卡片明确点击“获取可用模型”仍发真实网络刷新；改用绑定 `model-cache.json` 的现有 `ModelCache`。缓存继续按实例、地址和 Key 指纹隔离；成功结果按原缓存提交锁合并落盘，失败可返回相同凭据的旧候选，但卡片失败分支不合并、不覆盖草稿。原有草稿代次、URL/Key 归属检查保持不变。没有引入第二套缓存。

空闲和 Agent 运行中的 `ClearApiKey` 共用一个小函数：SecretStore 清除成功后，仅当实例 ID 为 `mimo` 且启用 MiMo 云端 TTS 时，通过现有 `SpeechRuntime.apply_settings()` 停止播报、取消合成并丢弃旧引擎。缺 Key 是清除后的预期不可用状态，错误通过现有播报状态回填显示，只更新实际运行状态，不覆盖尚未保存的语音设置草稿，也不将密钥清除误报成失败。恢复 Key 沿用既有保存后重建引擎路径。

其他 MiMo 实例、DeepSeek、兼容端点 Key 不触发此重建。本地 ONNX 后端也不停止或重建。已经发出的服务端请求不能被宣称撤销；沿用既有取消流和停止后续合成的语义。

## 为什么这样处理

磁盘缓存只能补充候选，不能同时充当覆盖用户配置的第二个权威源。只改“缓存落盘”不足以解决清 Key 后缓存不匹配导致目录消失，因此必须移除恢复函数中的破坏性过滤。相反，不需要新凭据系统或 TTS 状态机：复用现有停止、引擎构建与 UI 状态发布即可处理旧 Key 的运行时副本。

两个旧测试原先要求更换 Key/URL 后删除目录，这正是本轮改变的行为。测试现改为断言目录保留、仅明确获取后合并新候选、缓存仍账户隔离、URL 变化后旧能力降级；没有删除原缓存隔离断言。

## 验证结果

- 库测试：UI/配置/Session/卡片 79 项通过、3 项原标记忽略；模型目录与缓存 9 项通过；播报运行时 13 项通过，共 101 项通过。
- 六组集成测试：config_secrets 8、migration_and_config 9、pr8_model_discovery 1、pr8_probe_and_cache 3、settings_save 6、tts_mimo 12，共 39 项通过。
- 卡片保存含 Discovered/Unverified/Manual 的完整目录后，修改提示词、温度和上下文保存，再清 DeepSeek Key、重启、加载冲突旧缓存，均核对模型目录、默认、启用列表和元数据保持一致。
- 官方 MiMo 引擎初始化、清 Key、旧引擎不可继续 speak、播放终止、新 Key 重建恢复可用；非官方实例与本地后端保持原引擎和播放身份。使用假播放缓冲/合成引擎，不打开声卡、不访问真实供应商。
- 五实例 HTTP Mock 通过实际卡片获取函数写入同一持久缓存，核对各自凭据隔离。另用 HTTP Mock 验证有效缓存复用不发请求、明确刷新确实发请求、过期会尝试网络、失败仅回退同实例/地址/Key 的候选。
- 执行默认 CUDA Windows 构建、`cargo fmt --check`、`cargo clippy --all-targets`；不构建 CPU-only，不运行不相关的全仓测试。最终执行结果见 PR 描述。

## 未验证与边界

本轮没有使用真实供应商 Key，没有真实云端音质、真实声卡播放、真实 ONNX 推理或 GUI 清 Key 操作验收。引擎初始化/失效/恢复、播放取消和 UI 发布调用由自动化覆盖；不能当作实际播报验收。前轮已列出的输入法、系统 DPI、跨屏等 GUI 矩阵本轮未扩大。

不涉及 PR12 工具或 PR14/15/16，不新增应用运行时依赖，不发布 Release、不合并 PR。

最终默认 CUDA Windows 构建、fmt 检查和 clippy 全部通过（保留既有警告）；运行状态 UI 回填调整后，两项 Key 清除/恢复回归再次通过。
